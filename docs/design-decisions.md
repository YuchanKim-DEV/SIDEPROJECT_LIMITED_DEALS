# 설계 결정과 근거

면접에서 "왜 이렇게 했나"에 답하기 위한 문서. 답마다 **코드 위치와 실험 숫자**를 붙였다. 숫자는 모두 로컬 맥북 한 대에서 잰 값이라 절대값보다 비교가 의미 있다.

## 한눈에 보기
```
k6 ─→ gateway :8000 ── JWT 검증, Rate Limit(Redis), 서킷 브레이커 + 503
        ├─→ queue-service :8081 ── Redis Sorted Set 대기열, 초당 N명 입장, 입장권(TTL)
        ├─→ order-service :8082 ── 입장권 확인(회로, fail closed) → 멱등 키 → 재고 차감 + 주문 + Outbox (한 트랜잭션)
        │       └─ Outbox 릴레이 ─→ Kafka order-events (키 = 상품 id)
        │                              ├─→ notification-service :8083 (Inbox, DLT)
        │                              └─→ payment-service :8084 (Inbox → 모의 PG → 원장 + Outbox)
        │                                      └─ Kafka payment-events (키 = 주문 id) ─→ order-service: PAID / CANCELLED + 재고 복구
        └─ 관측: Prometheus, Loki, Grafana
```

---

## 1. 왜 Kafka인가
**문제**: 주문이 확정되면 알림, 결제(나중엔 정산, 배송)가 각자 처리해야 한다. 주문 서버가 이들을 직접 HTTP로 부르면, 하나가 느리거나 죽을 때 주문까지 실패하거나 느려진다.

**선택**: 주문 서버는 이벤트를 Kafka에 남기고 끝낸다. 받는 쪽은 각자 속도로 읽는다.
- **저장한다**: 받는 쪽이 꺼져 있어도 메시지가 디스크에 남는다. 다시 켜면 마지막으로 읽은 위치(오프셋)부터 이어 읽는다. 실험 04-D: 알림 서버를 끄고 주문 40건 → 켜자 4초 만에 40건 처리. 실험 08-D: 결제 서버를 주문 도중 껐다 켜도 100건 모두 결제.
- **여러 곳이 같은 이벤트를 따로 받는다**: 컨슈머 그룹이 다르면 각자 받는다. 알림(`notification-service`)과 결제(`payment-service`)가 같은 `order-events`를 읽는데, 결제를 붙일 때 주문 서버 코드를 고치지 않았다.
- **순서**: 같은 키는 같은 파티션으로 가서 순서가 지켜진다. 주문 이벤트는 상품 id, 결제 결과는 주문 id를 키로 썼다.

**다른 선택지**
| 선택지 | 안 쓴 이유 |
|---|---|
| HTTP 직접 호출 | 받는 쪽 장애가 주문으로 번진다. 재시도와 순서를 직접 만들어야 한다 |
| Redis Pub/Sub | 저장하지 않는다. 받는 쪽이 꺼져 있으면 사라진다 |
| Redis Streams | 저장과 컨슈머 그룹이 있지만, 디스크 기반 보관 기간과 파티션 확장, 생태계(Connect, CDC)는 Kafka가 낫다 |
| RabbitMQ | 작업 큐에는 좋지만, 같은 이벤트를 여러 곳이 다시 읽거나(리플레이) 오래 보관하는 데는 Kafka가 맞다 |

**대가**: 운영 부담(브로커, 파티션, 모니터링), 결과가 바로 반영되지 않음(최종 일관성: 주문 → 알림 평균 1.5초, 실험 04-A). 메시지는 **최소 한 번** 전달되므로 중복을 받는 쪽이 처리해야 한다(2번).

코드: `OutboxRelay`(order-service, payment-service), `OrderEventListener`(notification, payment), `PaymentResultListener`(order).

## 2. 중복 메시지는 어떻게 처리하나
**왜 생기나**: Outbox 릴레이는 Kafka에 보낸 뒤 "보냄" 표시를 한다. 그 사이에 죽으면 다음에 같은 이벤트를 또 보낸다. 컨슈머도 처리 후 오프셋 커밋 전에 죽으면 같은 메시지를 다시 받는다. "정확히 한 번 전달"은 없다고 보고, **받는 쪽이 같은 결과를 한 번만 만들게** 했다(멱등 컨슈머).

| 위치 | 방법 | 확인 |
|---|---|---|
| 알림, 결제 컨슈머 | **Inbox**: 처리한 eventId를 유니크 제약이 있는 테이블에 기록. 처리 결과와 **같은 트랜잭션** | 실험 04-C: 30건을 다시 보내도 알림 30건 그대로. 결제 테스트: 같은 이벤트 3번 → 결제 1, 원장 2줄, PG 호출 1 |
| 주문 서버의 결제 결과 처리 | **상태 전이**: `UPDATE orders SET status=? WHERE id=? AND status='PENDING_PAYMENT'`. 바뀐 줄이 0이면 이미 처리됨 | 테스트: 실패 결과 2번 + 늦게 온 성공 1번 → 재고는 한 번만 복구 |
| 결제 완료(컨슈머 vs 대사) | 상태 전이 `WHERE status IN (REQUESTED, UNKNOWN)`. 이긴 쪽만 원장과 이벤트를 남긴다 | 테스트: 대사를 두 번 돌려도 원장 2줄 |
| 원장 | `(payment_id, account, direction)` 유니크 | 같은 결제를 두 번 기록하면 DB가 거절 |
| PG | 가맹점 주문 번호 유니크(PG 쪽 멱등성) | 다시 요청해도 승인 한 번 |
| 사용자 재시도(주문 버튼 연타, 응답 유실) | **Idempotency-Key** + 유니크 제약 + 요청 지문(SHA-256) | 실험 02: 같은 키 동시 50번 → 주문 1건 |

Inbox와 상태 전이 중 무엇을 쓸지: 결과가 "새 행을 만든다"면 Inbox(무엇을 처리했는지 따로 기억해야 한다), 결과가 "상태를 한 방향으로 바꾼다"면 조건부 UPDATE가 더 단순하다.

## 3. 컨슈머가 실패하면 어떻게 복구하나
실패를 세 종류로 나눴다.

| 종류 | 예 | 대응 | 확인 |
|---|---|---|---|
| 컨슈머가 죽음 | 서버 재시작, 배포 | 오프셋은 처리에 성공해야 커밋된다. 다시 뜨면 마지막 커밋부터 읽는다. 중복은 2번이 막는다 | 실험 04-D, 08-D |
| 일시적 오류 | DB 순간 끊김 | 1초 간격 3번 재시도(`DefaultErrorHandler` + `FixedBackOff`) | |
| 처리할 수 없는 메시지(독 메시지) | 잘못된 데이터, 버그 | 재시도 후 **DLT(`order-events-dlt`)로 옮기고 다음 메시지로 넘어간다**. 같은 파티션의 뒤 메시지가 막히지 않는다. 원인을 고친 뒤 DLT에서 다시 보내면 Inbox가 중복을 막는다 | 실험 04-E: 실패 메시지 1건 DLT, 같은 시점 정상 3건 처리 |

결제에는 하나가 더 있다: **처리 도중에 죽은 경우**. 결제 서버는 [Inbox + 결제(REQUESTED) 저장] → [PG 호출] → [결과 저장] 순서다. PG 호출 전후에 죽으면 Inbox에는 기록돼 Kafka가 다시 보내도 건너뛴다. 그래서 **대사(reconciliation) 배치**가 30초 넘게 끝나지 않은 결제를 PG 조회 API로 확인해서 끝낸다. 메시지 재전송에만 기대지 않고, "상태를 보고 다시 맞추는" 경로를 따로 둔 것이다. 실험 08-C: PG 응답 30% 유실 → 대사가 34건을 승인으로 정리, 불일치 0.

코드: `KafkaErrorConfig`, `PaymentService`, `ReconciliationService`.

## 4. Redis와 DB가 어긋나면
**먼저 원칙**: Redis에는 **잃어도 되는 것**만 둔다. 돈과 재고의 정답은 MySQL에만 있다.

| Redis에 있는 것 | 잃거나 틀리면 | 대응 |
|---|---|---|
| 대기열 순번(Sorted Set) | 줄이 초기화된다(공정성 손실, 데이터 손실 아님) | 재고 판단은 DB가 하므로 초과 판매는 생기지 않는다 |
| 입장권(TTL 키) | 입장한 사람이 주문을 못 한다 | 확인할 수 없으면 주문을 받지 않는다(fail closed, 실험 05). 대기열을 건너뛴 주문이 생기지 않는 쪽을 골랐다 |
| Rate Limit 카운터 | 잠깐 한도가 풀린다 | 뒤에 대기열과 DB 방어선이 있다 |

**재고를 Redis에 두지 않은 이유**: Redis에서 먼저 재고를 빼면(DECR) 빠르지만, Redis와 DB 두 곳에 재고가 생겨 둘이 어긋날 수 있다(Redis는 뺐는데 DB 트랜잭션이 실패, Redis 장애 후 복구 시 값 차이). 이번 규모(초당 수백 건)에서는 DB 원자적 UPDATE로 충분했고(실험 01, 06), 대기열이 초당 입장 인원을 조절해서 DB에 오는 양을 묶어 두었다.

**만약 Redis 재고를 쓴다면**(10배 이상 트래픽):
- DB가 정답이고 Redis는 "통과시킬지" 판단하는 문지기로만 쓴다. Redis에서 통과해도 DB UPDATE가 최종 판단한다.
- 어긋남은 대사로 찾는다(주기적으로 DB 재고와 Redis 값을 비교해 Redis를 DB에 맞춘다). 결제 대사(8단계)와 같은 생각이다.
- 일반 캐시(상품 조회 등)는 쓰기 후 캐시 삭제 + 짧은 TTL로 어긋나는 시간을 제한한다.

**9단계의 품절 빠른 거절**도 Redis가 아니라 DB의 잠그지 않는 읽기를 썼다. 늦은 값을 읽어도 정답 경로(원자적 UPDATE)가 뒤에 있어서 안전하다.

## 5. 트래픽이 10배가 되면 어디가 먼저 터지나
측정한 숫자로 순서를 매겼다.

| 순서 | 병목 | 근거 | 대응 |
|---|---|---|---|
| 1 | **재고 한 행의 락** | 한 상품 초당 600건 → 처리 206~345건, p99 5.8~8.6초. 커넥션 풀 30으로 늘리면 **더 나빠짐**(225건). 상품 10개로 나누면 592건, p99 0.78초 (실험 06) | 대기열 입장 속도로 DB에 오는 양을 묶는다(10배 손님 = 더 긴 대기, DB 부하는 같음). 그래도 부족하면 재고를 여러 행(버킷)으로 쪼개거나 Redis 문지기 |
| 2 | **락 안에서 하는 일** | 품절 뒤 요청이 락 앞에 줄 서고, 락을 잡은 트랜잭션이 0.5~1.7초씩 걸림 (실험 09) | 품절 빠른 거절, 재고 UPDATE를 트랜잭션 맨 끝으로, open-in-view 끄기 |
| 3 | **숨은 기본값** | Spring Cloud CircuitBreaker의 벌크헤드(동시 25개)가 1,000명에서 즉시 거절 338건 (실험 06) | 끄고, 들어오는 양은 대기열과 Rate Limit이 조절 |
| 4 | **게이트웨이 회로의 판단 창** | "최근 20건" 기준은 초당 1,000건에서 0.02초만 보고 열림 (실험 06) | 시간 기준 창(10초, 최소 100건) |
| 5 | DB 커넥션 총량 | 서버를 늘리면 `서버 수 × 풀 크기`가 MySQL `max_connections`를 넘는다 | 풀은 작게, 서버 수와 함께 계산. 읽기는 복제본으로 |
| 6 | Kafka 파티션 수 | 파티션 3개 = 같은 그룹에서 동시에 읽는 컨슈머 최대 3대 | 파티션을 미리 넉넉히(늘리면 키 순서가 섞이는 시점이 생긴다) |
| 7 | 노드 자원 | HPA가 대기열 서버를 2 → 6대로 늘렸지만 6번째는 메모리 부족으로 Pending (실험 07) | Cluster Autoscaler(노드 증설). 시작 시각을 아는 오픈런은 미리 늘려 두기(예약 스케일) |

**늘리기 쉬운 것**: gateway, queue-service(상태가 Redis에 있음), notification, payment(컨슈머는 파티션 수까지). **늘리기 어려운 것**: MySQL(쓰기 1대), 재고 한 행. 그래서 설계 전체가 "**쓰기 하나에 오는 양을 앞에서 줄이는**" 방향이다: Rate Limit → 대기열 입장 속도 → 품절 빠른 거절 → 원자적 UPDATE.

## 그 밖의 결정
| 질문 | 답 | 근거 |
|---|---|---|
| 재고 차감은 왜 원자적 UPDATE인가 | 읽고-빼고-쓰기는 동시에 오면 갱신 손실(재고 100에 965건 판매). 비관적 락은 비슷하게 빠르지만 락을 잡는 구간이 길다. 낙관적 락은 충돌이 잦으면 재시도가 일을 키운다(평균 2초) | 실험 01, 06 |
| 왜 MSA인가 | 대기열(트래픽 폭주, Redis)과 주문(정합성, MySQL)은 늘리는 방식과 장애 성격이 다르다. 대기열만 늘리기(HPA) 위해 나눴다. 대가는 분산 트랜잭션(Saga)과 운영 복잡도 | 실험 07, 08 |
| 결제는 왜 Saga인가 | 주문 DB와 결제 DB를 한 트랜잭션으로 묶을 수 없다. 각자 끝내고 이벤트로 잇고, 실패하면 보상(주문 취소 + 재고 복구) | 실험 08-B: 취소 31건, 재고 31 복구 |
| PG 시간 초과는 왜 실패가 아닌가 | PG는 승인했을 수 있다. 실패로 처리하면 돈은 빠졌는데 주문은 취소된다. UNKNOWN으로 두고 PG에 조회해서 정한다 | 실험 08-C |
| 원장은 왜 복식부기인가 | 차변 합 = 대변 합 = 승인 합계라는 규칙 하나로 누락과 중복을 찾는다. 추가만 하므로 정산을 다시 계산해도 같다 | 실험 08 대사 |
| 장애 시 왜 재시도하지 않나(서버 안에서) | 느린 서버에 재시도하면 요청이 2배, 3배가 된다(retry storm). 빨리 실패하고, 재시도는 정해진 곳(Outbox, 컨슈머, 클라이언트의 Retry-After)에서만 | 실험 05, 06 |
| 남의 주문은 왜 404인가 | 403은 "있다"를 알려 준다. 번호를 올려 가며 다른 사람 주문을 찾는 공격(IDOR) | 실험 09 |

## 아직 하지 않은 것
- 분산 추적(OpenTelemetry): 요청 하나가 서버 5개를 지나는 경로를 한 줄로 보기.
- 서버를 따로 띄운 환경에서의 측정(EKS 등). 지금 숫자는 노트북 한 대.
- 환불과 부분 취소, 리프레시 토큰, 서비스 간 인증.
