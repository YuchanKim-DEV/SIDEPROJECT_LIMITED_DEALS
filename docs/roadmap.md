# Roadmap

LIMITED_DEALS의 학습 로드맵이다. 계획은 바뀔 수 있으므로 이 파일에서 따로 관리하고, 바뀔 때마다 아래 변경 이력에 남긴다.

## 목표

백엔드에서 반드시 갖춰야 할 항목(대용량 데이터, 데이터 유실 방지, 동시성, 멱등성 등)을 **직접 구현하고 겪어 보면서** 깊이 있게 익힌다. 소재는 **한정 특가**(한정 수량 상품에 요청이 몰리는 상황)다.

## 진행 방식

- 구현과 세팅은 **내가 직접** 한다. Claude는 개념 설명, 힌트, 결과 확인, 리뷰를 맡는다.
- 문제를 먼저 겪고(재현), 그다음에 기술을 도입한다.
- 한 번에 한 단계, 작은 단위로 진행한다.

## 정해진 기술

| 항목 | 선택 |
|---|---|
| 언어, 프레임워크 | Java 25, Spring Boot 4.1.1 |
| DB | **MySQL 8.4.11 (InnoDB)**, 이미지 `mysql:8.4.11`(버전 고정), Docker Compose로 실행 |
| 아직 미정 | Flyway, Testcontainers 도입 여부 (0단계에서 결정) |

## 단계

| 단계 | 주제 | 다루는 성질 | 상태 |
|---|---|---|---|
| 0 | 기술 스택 세팅 | MySQL 드라이버, Docker Compose, datasource, (Flyway, Testcontainers) | 예정 |
| A | 재고 동시성 | 트랜잭션, 격리수준, 락(원자적 UPDATE, 비관적, 낙관적), 예외 처리와 표준 에러 응답 | 예정 |
| B | 주문 멱등성 | 멱등 키, 유니크 제약 | 예정 |
| C | 대용량 조회와 적재 | 인덱스, N+1, 커서 기반 페이징, JDBC 배치, Spring Batch | 예정 |
| D | Redis | 캐시, 분산 락, Rate Limiting | 예정 |
| E | 이벤트 신뢰성 | Kafka, Outbox, 멱등 컨슈머, DLQ | 예정 |
| F | 장애 대응 | 타임아웃, 재시도(백오프), 서킷 브레이커 | 예정 |
| G | 관측과 부하 테스트 | 구조화 로그, 메트릭(Micrometer), k6 | 예정 |
| H | 보안 | 인증/인가(JWT), 입력 검증 | 예정 |

상태는 `예정`, `진행 중`, `완료`로 쓴다.

## 각 단계가 답해야 할 질문

| 단계 | 질문 |
|---|---|
| A | 재고 1개에 100명이 동시에 주문하면 몇 건이 성공하는가? 락 방식마다 성능은 어떻게 다른가? |
| B | 결제 요청을 두 번 보내면 주문은 몇 건 생기는가? 동시에 두 번이면? |
| C | 데이터가 수백만 건일 때 조회가 얼마나 느려지고, 인덱스와 페이징으로 얼마나 개선되는가? |
| D | 캐시를 쓰면 정합성은 어떻게 지키는가? 캐시가 한꺼번에 만료되면? |
| E | 주문은 저장됐는데 이벤트 발행이 실패하면? 같은 이벤트가 두 번 오면? |
| F | 외부 결제 서버가 느려지면 우리 서버는 어떻게 되는가? |
| G | 장애가 났을 때 원인을 얼마나 빨리 찾을 수 있는가? 초당 몇 건까지 버티는가? |
| H | 남의 주문을 조회할 수 있는가? |

## 변경 이력

| 날짜 | 변경 |
|---|---|
| 2026-10-12 | 최초 작성. DB는 MySQL 8로 결정. 장애 대응(F)과 보안(H)을 추가해 A~H로 확정 |
| 2026-10-12 | MySQL 버전을 8.4.11(LTS)로 구체화. `latest`는 혁신 릴리스(26.x)라 사용하지 않고 버전을 고정 |
