# Roadmap

LIMITED_DEALS의 기획서이자 학습 로드맵이다. 계획은 바뀔 수 있으므로 이 파일에서 따로 관리하고, 바뀔 때마다 아래 변경 이력에 남긴다.

## 1. 한 줄 소개

**한정판 "온라인 오픈런"을 버티는 서버.** 인기 상품이 풀리는 순간 수만 명이 몰려도 줄을 세우고, 재고를 정확히 팔고, 주문을 하나도 잃지 않는 백엔드를 MSA로 만든다.

## 2. 왜 이 주제인가

| 이유 | 설명 |
|---|---|
| 면접 단골 문제가 한 번에 생김 | 동시성, 멱등성, 유실 방지, 트래픽 폭주 |
| 목표 회사들이 실제로 다루는 문제 | 토스·쿠팡의 "정합성", 토스·티빙·당근의 "순간 트래픽 급증", 공통의 "장애 대응" |
| 숫자로 증명 가능 | "1만 명 동시 주문 → 초과 판매 0건, p99 응답 ○ms"처럼 결과를 보여줄 수 있음 |

## 3. 사용자 흐름

```
① 오픈 시각에 접속 → ② 사람이 많으면 번호표를 받고 대기 ("내 순번 3,421번")
→ ③ 순서가 오면 N분짜리 입장권 발급 → ④ 구매(재고 차감) → ⑤ 주문 확정 이벤트 발행
```

화면은 꾸미지 않는다. **테스트 시작 버튼, 순번 화면, 지표·로그 대시보드**만 만든다.

## 4. 구상도

```
                 [k6] 1만~10만 명 동시 요청
                          │
                 ┌────────▼────────┐
                 │  gateway :8080  │  입구. Rate Limit(초당 N건, Redis)
                 └───┬─────────┬───┘
        /api/queue/** │         │ /api/orders/**
       ┌──────────────▼──┐   ┌──▼──────────────────────┐
       │ queue-service    │   │ order-service            │
       │ :8081            │   │ :8082                    │
       │ 번호표, 입장권     │   │ 재고 차감(락) + 주문      │
       │                  │   │ + outbox (한 트랜잭션)    │
       └──────┬───────────┘   └──────┬──────────────────┘
              ▼                      ▼            │ 릴레이
           [Redis]               [MySQL]          ▼
                                            [Kafka] 상품 id 기준 순서 보장
                                                  ▼
                                    [컨슈머] Inbox로 중복 제거 → 처리

  관측: Prometheus(지표) + Loki(로그) → Grafana 대시보드
  실행: 로컬은 docker compose → 나중에 Kubernetes
```

## 5. 기술 스택과 선택 이유

2026-11-02에 지원하려는 회사 공고 19개(토스, 쿠팡, 티빙, 당근, 카카오페이)를 분석해 공통으로 나오는 기술을 골랐다.

| 기술 | 역할 | 근거(공고) |
|---|---|---|
| Java 25 + Spring Boot 4.1 | 서버 3개 | 전 회사 공통 (Kotlin은 토스·카카오페이 기본, 이번엔 Java 유지) |
| Spring Cloud Gateway | 입구, 라우팅, Rate Limit | 토스 SRE, 티빙, 쿠팡 |
| MySQL 8.4.11 | 주문, 재고, outbox | 토스 전부, 카카오페이 |
| Redis 8.8.4 | 번호표, 입장권, Rate Limit | 토스 전부, 카카오페이, 쿠팡 |
| Kafka | 주문 이벤트 전달 | 거의 전 회사 |
| Prometheus + Grafana + Loki | 지표, 로그 | 토스 SRE, 쿠팡 |
| k6 | 부하 테스트 | 토스 SRE(성능 테스트) |
| Docker, Kubernetes | 실행, 확장 | 쿠팡, 토스, 티빙, 카카오페이 |

## 6. 계획표

| 단계 | 할 일 | 확인할 질문 | 상태 |
|---|---|---|---|
| 0. 기반 | 서버 3개 분리(멀티 모듈), MySQL·Redis | 입구가 각 서버로 안내하는가? | 완료 |
| 1. 재고 동시성 | 초과 판매 재현 → 락 3가지 비교 | 재고 1개에 1만 명이 사면 몇 건이 팔리나? | 예정 |
| 2. 주문 멱등성 | 멱등 키 + 유니크 제약 | 결제 버튼을 동시에 두 번 누르면? | 예정 |
| 3. 대기열 | 번호표, 입장 제어, 입장권, Rate Limit, 순번 화면 | 10만 명이 몰려도 서버가 안 죽나? | 예정 |
| 4. 이벤트 신뢰성 | Kafka, Outbox, Inbox, DLQ | 서버가 죽어도 주문 이벤트가 사라지지 않나? | 예정 |
| 5. 장애 대응 | 타임아웃, 재시도, 서킷 브레이커, 서버 강제 종료 실험 | 한 서버가 죽으면 나머지는 버티나? | 예정 |
| 6. 관측과 부하 | Grafana 대시보드, 병목 찾기(스레드, DB 커넥션), 가상 스레드 | 초당 몇 건까지 버티고, 어디서 무너지나? | 예정 |
| 7. 확장과 배포 | Docker 이미지, Kubernetes, 대기열 서버만 늘리기 | 대기열 서버를 늘리면 처리량이 얼마나 오르나? | 예정 |
| 8. 결제·정산 | 모의 결제, 원장, 대사 배치, Saga | 주문, 결제, 재고 숫자가 항상 맞나? | 보류 |
| 9. 보안 | 로그인(JWT), 입력 검증 | 남의 주문을 볼 수 있나? | 보류 |

상태는 `예정`, `진행 중`, `완료`, `보류`로 쓴다.

## 7. 단계마다 남길 결과물

1. **측정 숫자**: 개선 전후 비교(초과 판매 건수, 처리량, p99 응답 시간)
2. **장애 보고서(Post-mortem)**: 무엇이 왜 무너졌고 어떻게 막았는지
3. **블로그 글**: 단계마다 1편

## 8. 위험과 대응

| 위험 | 대응 |
|---|---|
| MSA가 복잡해서 핵심 학습(동시성, 멱등성)이 늦어짐 | 서버는 3개로 시작하고, 필요할 때만 늘린다 |
| 노트북 한 대로는 1만 명 재현이 어려움 | 1천 → 5천 → 1만으로 올리면서 무너지는 지점을 찾는다. 큰 규모는 7단계(Kubernetes)에서 |
| 8080 포트를 다른 프로젝트가 사용 중 | 실행할 때 포트를 바꾸거나 그 앱을 끈다 |

## 9. 진행 방식

- 작업(설정, 코드, 테스트, 브랜치, 머지)은 Claude가 하고, 사용자는 검수한다.
- 문제를 먼저 겪고(재현), 그다음에 기술을 도입한다.
- 한 번에 한 단계, 작은 단위로 진행한다.

| 날짜 | 변경 |
|---|---|
| 2026-10-12 | 최초 작성. DB는 MySQL 8로 결정. 장애 대응(F)과 보안(H)을 추가해 A~H로 확정 |
| 2026-10-12 | MySQL 버전을 8.4.11(LTS)로 구체화. `latest`는 혁신 릴리스(26.x)라 사용하지 않고 버전을 고정 |
| 2026-11-04 | 공고 분석을 바탕으로 **MSA와 온라인 오픈런**으로 전면 개편. 단일 앱 기준 A~H를 0~9단계로 교체. 결제·정산과 보안은 보류. 진행 방식을 "Claude가 작업, 사용자가 검수"로 변경 |
