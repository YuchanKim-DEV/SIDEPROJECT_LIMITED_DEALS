# 실험 05: 장애 대응 (시간 제한, 서킷 브레이커, 503 안내)

한 서버가 느려지거나 죽었을 때, 그 서버를 부르는 쪽까지 같이 느려지거나 무너지지 않는지 본다.

## 장치
| 위치 | 장치 | 설정 |
|---|---|---|
| order-service → queue-service (입장권 확인) | 연결·응답 시간 제한 | 연결 300ms, 응답 500ms |
| 〃 | 서킷 브레이커 (Resilience4j) | 최근 20번 중(최소 10번) 실패나 느린 호출(300ms 초과)이 50% 이상이면 열림, 5초 뒤 시험 호출 3번 |
| 〃 | 실패 시 정책 | 확인할 수 없으면 주문을 받지 않음(fail closed, 503) |
| gateway → 모든 서버 | 서킷 브레이커 + 3초 시간 제한 | 실패하면 `/fallback/{서버}`로 503 + `Retry-After: 5` + 안내 문구 |
| gateway SSE 순번 스트림 | 서킷 브레이커 제외 | 오래 열려 있는 연결이라 3초 제한을 걸지 않음 |
| queue-service | 장애 스위치(실험용) | `CHAOS_ENABLED=true`일 때 `POST /api/queue/admin/chaos?validateDelayMs=2000` |

## 다시 돌려보기
```bash
docker compose up -d && ./gradlew bootJar
scripts/load/resilience.sh   # 서버를 직접 띄우고 끈다
```

## 결과 (2026-11-05, 로컬)
| 실험 | 결과 |
|---|---|
| 1. 정상 | 주문 201, 0.03초 |
| 2. 대기열 서버를 2초씩 느리게 | 처음 7건은 **0.5초**(응답 시간 제한)에 503. 7번째에서 **회로 열림**(정상 3건 + 실패 7건 = 10건 중 70% 실패). 이후 8건은 대기열 서버를 부르지 않고 **0.003초**에 503 |
| 3. 대기열 서버 복구 + 6초 대기 | 시험 호출 3건이 성공해 **회로 닫힘**, 주문 201, 0.02초 |
| 4. 대기열 서버 종료 후 게이트웨이로 조회 | 첫 건 0.59초, 이후 **0.005초**에 503 + 안내 문구. 3단계에서 나왔던 **500이 503으로 바뀜** |
| 5. 주문 서버 종료 후 게이트웨이로 조회 | 503, 0.009초 |

## 왜 필요한가
- **시간 제한이 없으면**: 대기열 서버가 2초씩 걸리면 주문 요청도 2초씩 붙잡힌다. 주문 서버의 요청 처리 스레드(기본 200개)가 모두 기다리는 데 쓰이면, 대기열과 상관없는 요청까지 받을 수 없게 된다. 느린 서버 하나가 부르는 쪽 전체를 무너뜨리는 **연쇄 장애**다.
- **시간 제한만 있으면**: 매번 0.5초씩 기다렸다가 실패한다(실험 2의 처음 7건). 요청이 몰리면 0.5초 × 요청 수만큼 스레드가 계속 묶인다.
- **서킷 브레이커가 있으면**: "지금 저쪽은 안 된다"는 걸 기억하고 한동안 부르지 않는다. 실패를 0.003초에 돌려줘서 스레드가 묶이지 않고, 아픈 서버에 요청을 계속 보내 더 아프게 만들지도 않는다. 5초 뒤 조금만 시험해 보고 괜찮으면 원래대로 돌아간다(실험 3).
- **왜 재시도(retry)는 넣지 않았나**: 느린 서버에 재시도하면 요청이 2배, 3배로 늘어 오히려 장애를 키운다(retry storm). 입장권 확인은 사용자가 다시 누르면 되는 요청이라, 서버 안에서는 재시도하지 않고 빨리 실패시킨다. 재시도가 필요한 곳(Outbox 발행, 컨슈머)은 이미 정해진 간격과 횟수로 한다.
- **fail closed와 fail open**: 대기열을 확인할 수 없을 때 주문을 받으면(fail open) 판매는 계속되지만 대기열을 건너뛴 사람이 재고를 가져간다. 오픈런은 공정성이 중요해서 거절한다(fail closed). 대신 대기열이 죽으면 판매도 멈춘다. 서비스 성격에 따라 반대로 고를 수 있는 선택이다.

## 구현 중 겪은 문제
서킷 브레이커 테스트가 처음에 실패했다(10번 실패했는데도 회로가 안 열림). 테스트가 Resilience4j 레지스트리에서 회로를 **먼저 꺼내는** 바람에, 우리 설정(최소 10번)이 아니라 **기본 설정(최소 100번)**으로 만들어졌다. 회로는 처음 만들어질 때의 설정을 계속 쓴다. 실제 호출이 먼저 회로를 만들게 테스트 순서를 바꿨다. 운영 코드에서도 다른 곳이 같은 이름의 회로를 먼저 만들지 않도록 주의해야 한다.

## 한계
- 회로는 서버마다 따로 기억한다. 주문 서버가 여러 대면 각자 실패를 세다가 따로 열린다.
- 게이트웨이의 서킷 브레이커는 연결 실패와 시간 초과만 실패로 센다. 뒤쪽 서버가 500을 돌려주는 경우는 그대로 전달한다.
