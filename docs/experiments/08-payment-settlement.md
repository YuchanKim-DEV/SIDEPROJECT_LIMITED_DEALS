# 실험 08: 결제·정산 (Saga, 원장, 대사)

주문, 결제, 재고 숫자가 **항상 맞는지** 본다. PG(결제 대행사)가 거절하거나, 승인해 놓고 응답을 잃어버리거나, 결제 서버가 죽어도 맞아야 한다.

## 구조 (Saga, 코레오그래피)
```
order-service                         payment-service (8084)                     모의 PG (바깥 시스템)
 재고 차감 + 주문(PENDING_PAYMENT)
 + Outbox ── order-events ──────────→ [tx1] Inbox + 결제(REQUESTED)
                                      [tx 밖] PG 승인 요청 ─────────────────────→ 승인/거절 기록(자기 트랜잭션)
                                      [tx2] 결과 반영
                                        승인: APPROVED + 원장 2줄 + Outbox
                                        거절: FAILED + Outbox
                                        응답 없음: UNKNOWN (끝내지 않음)
 결과 반영 ←──────── payment-events ── Outbox 릴레이
  PaymentCompleted → PAID
  PaymentFailed    → CANCELLED + 재고 되돌림(보상)
                                      대사(30초마다): 오래 끝나지 않은 결제를 PG에 조회해 끝냄,
                                      PG 승인 목록 ↔ 우리 결제, 원장 차변 = 대변 = 승인 합계 확인
                                      정산: 원장의 하루 매출 - PG 수수료(3%)
```

| 장치 | 무엇을 막나 |
|---|---|
| 주문 상태 전이 `UPDATE ... WHERE status='PENDING_PAYMENT'` | 같은 결제 결과가 두 번 와도 재고를 두 번 되돌리지 않는다. 늦게 온 반대 결과도 무시한다 |
| 결제 상태 전이 `WHERE status IN (REQUESTED, UNKNOWN)` | 컨슈머와 대사가 같은 결제를 동시에 끝내도, 원장 기록과 이벤트는 이긴 한쪽만 남긴다 |
| PG 멱등성(주문 번호 `order-{id}` 유니크) | 다시 요청해도 두 번 승인되지 않는다 |
| PG 호출을 트랜잭션 밖에서 | 느린 외부 호출 동안 DB 커넥션을 잡고 있지 않는다(6단계에서 커넥션 대기가 병목이었다) |
| UNKNOWN 상태 | 응답이 없다고 실패로 처리하면, 돈은 빠졌는데 주문은 취소된다 |
| 복식부기 원장(추가만, `(payment_id, account, direction)` 유니크) | 기록이 빠지거나 두 번 들어가면 차변 ≠ 대변으로 드러난다 |
| 결제 Inbox, 결제 Outbox | 4단계와 같은 방식: 중복 이벤트를 거르고, 결과 이벤트를 잃지 않는다 |

## 왜 이렇게 했나
- **왜 Saga인가**: 주문(order DB)과 결제(payment DB)는 다른 서버, 다른 DB라서 한 트랜잭션으로 묶을 수 없다. 2PC(분산 트랜잭션)는 한쪽이 느리면 양쪽이 락을 잡고 기다리고, Kafka와는 함께 쓸 수 없다. 대신 각자 자기 트랜잭션을 끝내고 이벤트로 다음 단계를 부르며, 실패하면 앞 단계를 **되돌리는 보상 트랜잭션**(주문 취소 + 재고 복구)을 실행한다. 잠깐 동안은 "재고는 빠졌는데 결제는 아직"인 상태가 있다(최종 일관성).
- **왜 코레오그래피인가(오케스트레이션이 아니라)**: 단계가 둘(주문 → 결제)이라 중앙 조정자를 따로 두면 오히려 복잡하다. 단계가 늘어나면(쿠폰, 포인트, 배송) 흐름이 이벤트에 흩어져 보기 어려워지므로, 그때는 오케스트레이터(상태 기계)를 둔다.
- **시간 초과는 실패가 아니다**: 실험 C가 핵심이다. PG는 승인했는데 우리는 응답을 못 받았다. 여기서 실패로 처리하면 고객 돈은 빠졌는데 주문은 취소된다. "모름(UNKNOWN)"으로 남겨 두고, PG 조회 API로 확인한 뒤 끝낸다. 실제 결제 시스템에서 가장 많이 나오는 장애 유형이다.
- **왜 원장인가**: 결제 테이블의 상태는 덮어쓰지만 원장은 추가만 한다. 돈이 언제, 왜 움직였는지 이력이 남고, 차변 = 대변이라는 규칙 하나로 기록 누락이나 중복을 찾을 수 있다. 정산도 원장에서 계산해서, 다시 계산해도 같은 값이 나온다.
- **돈은 정수로**: 금액은 원 단위 `long`. `double`은 0.1 + 0.2 ≠ 0.3 같은 오차가 있다. 수수료처럼 나눗셈이 생기면 반올림 규칙(여기서는 내림)을 정해서 테스트로 고정했다(33,333원의 3% = 999.99 → 999원).
- **대사가 자동으로 고치는 것과 알리기만 하는 것**: "끝나지 않은 결제"는 PG에 물어보면 답이 정해져 있어서 자동으로 끝낸다. "PG에는 없는데 우리는 승인" 같은 불일치는 원인을 모르므로 고치지 않고 ERROR 로그와 지표(`payment.reconciliation.mismatches`)로 알린다. 잘못 고치면 돈 문제가 더 커진다.

## 구현 중 겪은 문제
- **Inbox만으로는 부족했다.** 처음 설계에서는 Inbox 기록과 결제 생성을 커밋한 뒤 PG를 부른다. 그 사이에 서버가 죽으면 Kafka는 같은 이벤트를 다시 보내지만 Inbox가 "이미 처리함"으로 건너뛴다. 결제는 REQUESTED로 영원히 남는다. 그래서 대사가 오래된 REQUESTED도 PG에 조회해서 끝내도록 했다(실험 D에서 이 경로가 쓰였다).
- **결제 서버를 처음 붙일 때 읽기 시작 위치**: `auto-offset-reset: earliest`면 결제 기능이 생기기 전에 쌓인 주문 이벤트 수만 건까지 결제를 시도한다. 새 컨슈머 그룹은 `latest`로 시작하게 했다. 대신 결제 서버가 처음 뜨기 전에 들어온 주문은 결제 대기로 남는다(운영에서는 배포 순서로 막는다: 결제 서버 먼저).

## 한계
- 결제 서버가 PG 응답을 받기 전에 대사가 같은 결제를 "PG 기록 없음 → 실패"로 끝낼 수 있다(PG 응답이 30초보다 느릴 때). 이때는 PG 승인 + 우리 실패로 대사에 불일치가 잡힌다. 운영에서는 PG 취소(환불) API로 보상한다. 여기서는 알리기만 한다.
- 대사는 전체 테이블을 읽는다. 운영에서는 날짜별로 나눠서, PG가 주는 정산 파일과 비교한다.
- 환불, 부분 취소, 결제 수단별 수수료는 없다.
- 결제 결과 알림(notification-service)은 아직 주문 접수 이벤트만 받는다.
