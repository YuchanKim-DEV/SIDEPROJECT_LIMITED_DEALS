# 실험 06: 관측(메트릭, 로그, 대시보드)과 k6 부하 테스트

"빠르다, 버틴다"를 느낌이 아니라 숫자로 말하기 위해 관측 도구를 붙이고, k6로 부하를 걸어 병목을 찾는다.

## 구성
| 도구 | 역할 | 주소 |
|---|---|---|
| Micrometer + Prometheus | 서버 4개의 메트릭을 5초마다 수집 (`/actuator/prometheus`) | http://localhost:9090 |
| Loki (loki-logback-appender) | 서버 4개의 로그를 한곳에 모음. 테스트에서는 보내지 않음(`logback-test.xml`) | http://localhost:3100 |
| Grafana | 대시보드 "LIMITED_DEALS" 자동 등록 (대기 인원, 초당 입장, Outbox 대기, 회로 상태, 서버별 p95/p99, 재고 방식별 p99, 커넥션 풀, 스레드, 로그) | http://localhost:3000 |
| k6 | 부하 생성. 맥에 설치된 k6를 우선 사용(`brew install k6`) | `scripts/load/k6.sh` |

응답 시간 분포(p95, p99)를 보려고 `http.server.requests`에 히스토그램을 켰다(`percentiles-histogram`). 평균은 느린 소수를 숨기기 때문이다.

## 다시 돌려보기
```bash
docker compose up -d && ./gradlew bootJar
scripts/run-local.sh start --spring.jpa.show-sql=false
scripts/load/k6.sh order-strategies.js -e STRATEGY=atomic -e RATE=600 -e DURATION=20s               # 한 상품
scripts/load/k6.sh order-strategies.js -e STRATEGY=atomic -e RATE=600 -e DURATION=20s -e PRODUCTS=10 # 상품 10개
scripts/run-local.sh restart order-service   # 아래 오픈런은 ENTRY_TOKEN_REQUIRED=true로 띄운 뒤
scripts/load/k6.sh open-run.js -e VUS=1000 -e STOCK=100
```

## 결과 (2026-11-05, 로컬 맥북 한 대, 모든 서버와 DB가 같은 장비)

### A. 재고 차감 방식별 응답 시간 (한 상품, 초당 300건, 20초)
| 방식 | 결과 |
|---|---|
| naive | 빠르지만 재고가 틀린다(실험 01). 비교 대상일 뿐 |
| atomic (`UPDATE ... WHERE stock >= ?`) | 평균 약 0.1~0.3초. 실행마다 흔들림 |
| pessimistic (`SELECT ... FOR UPDATE`) | atomic과 비슷 |
| optimistic (버전 + 재시도) | 평균 약 2초, 보내지 못한 요청 발생. 충돌이 잦으면 재시도가 일을 더 만든다 |

결론: 한 행에 몰리는 오픈런에서는 낙관적 락이 맞지 않는다. 충돌이 드문 곳(예: 회원 정보 수정)에 쓰는 방식이다.

### B. 한 행의 한계 (atomic, 초당 600건)
| 상황 | 처리량 | p99 | 비고 |
|---|---|---|---|
| 한 상품 (1회차) | 약 345건/초 | 5.8초 | 커넥션 10개 모두 사용 중, 190개 대기. 요청 스레드 200개 모두 사용 중 |
| 한 상품 + 커넥션 풀 30개 | 약 225건/초 | 8.6초 | **더 나빠짐** |
| 한 상품 (재실행) | 206건/초 | 8.6초 | 보내지 못한 요청 6,039건 |
| 상품 10개에 나눔 (1회차) | 약 555건/초 | 1.47초 | |
| 상품 10개에 나눔 (재실행) | 592건/초 | 0.78초 | 거의 목표치(600) |

- **병목은 서버가 아니라 한 행의 락이다.** 같은 행을 바꾸는 UPDATE는 한 번에 하나씩만 된다. 앞 트랜잭션이 커밋할 때까지 뒤는 줄을 선다.
- **커넥션을 늘리면 더 나빠진다.** 커넥션이 많아지면 같은 행을 기다리는 트랜잭션만 늘어나고, DB 안에서 락 대기와 문맥 전환이 커진다. "느리면 풀을 늘린다"는 병목이 DB 커넥션 수일 때만 맞다. 그래서 10개로 되돌렸다.
- **행을 나누면 풀린다.** 상품 10개(서로 다른 행)로 나누자 같은 서버, 같은 풀에서 처리량이 2~3배가 됐다. 한 상품의 재고를 여러 행(버킷)으로 쪼개거나, Redis에서 먼저 차감하고 DB에는 나중에 반영하는 방식이 이 원리다.
- 같은 조건에서도 실행마다 숫자가 크게 흔들린다(345 vs 206). 로컬 장비 한 대에서 k6, 서버 4개, MySQL, Kafka가 CPU를 나눠 쓰기 때문이다. 절대값보다 **비교(1개 vs 10개)**를 봐야 한다.

### C. 오픈런 전체 흐름 (게이트웨이 경유, 1,000명, 재고 100)
대기열 진입 → 순번 확인(2~3초 간격, 흩뜨림) → 입장권 → 주문(멱등 키로 재시도). 사용자는 503/429를 받으면 잠시 뒤 다시 시도한다.

| 단계 | 결과 |
|---|---|
| 처음 (Docker로 k6 실행) | 응답 시간과 실패가 비정상적으로 큼 → k6를 맥에서 직접 실행하도록 변경 |
| 게이트웨이 회로를 "최근 20건" 기준으로 | 순간 지연에 회로가 열리면서 대기열 전체가 503 |
| "최근 10초, 최소 100건" 기준으로 변경 | 회로는 안정. 그래도 즉시 실패하는 503이 남음 |
| 원인: 숨은 벌크헤드 | 게이트웨이 로그에 `BulkheadFullException` order-service 247건, queue-service 91건 |
| 벌크헤드 끈 뒤 (2회 실행) | 두 번 모두 **구매 100, 품절 900**, 벌크헤드 거절 0건. 요청 p99 1.46초 / 0.87초 |

## 구현 중 겪은 문제
- **Docker로 돌린 k6가 결과를 왜곡했다.** 맥의 Docker는 가상 머신 안에서 돌아서, 컨테이너 안의 k6가 보내는 모든 연결이 Docker 네트워크 중계를 거친다. 연결 1,000개가 몰리자 중계가 병목이 되어 서버가 아니라 측정 도구가 느렸다. 부하 도구는 측정 대상과 다른 병목을 만들지 않아야 한다.
- **서킷 브레이커가 너무 예민했다.** 실험 05의 "최근 20건" 기준은 초당 1,000건이 오는 입구에서는 0.02초 동안의 기록만 보고 판단하는 셈이다. 순간적인 지연 몇 건에 회로가 열렸다. 트래픽이 많은 곳은 시간 기준 창(최근 10초)과 최소 호출 수(100건)를 둔다.
- **아무도 설정하지 않은 동시 호출 제한.** Spring Cloud CircuitBreaker(Resilience4j)는 회로와 함께 **벌크헤드(동시 호출 최대 25개)**를 기본으로 건다. 설정 파일 어디에도 없어서 처음에는 회로가 열린 것으로 오해했다. 게이트웨이 fallback이 "왜 실패했는지"(`CIRCUITBREAKER_EXECUTION_EXCEPTION_ATTR`)를 로그로 남기게 바꾸고 나서야 `BulkheadFullException`이 보였다. 들어오는 양은 대기열 입장 속도와 Rate Limit이 이미 조절하고, 느린 호출은 시간 제한과 회로가 끊으므로 게이트웨이와 주문 서버 모두 끄도록 했다(`spring.cloud.circuitbreaker.bulkhead.resilience4j.enabled=false`).
- **사용자 재시도도 설계의 일부다.** 503에 `Retry-After: 5`를 주고, k6 사용자는 기다렸다가 같은 멱등 키로 다시 주문한다. 순번 확인도 모두 같은 순간에 오지 않게 2~3초 사이로 흩뜨렸다. 모두가 같은 박자로 재시도하면 그 자체가 순간 폭주가 된다.

## 한계
- 로컬 장비 한 대라 절대 수치는 의미가 작다. 서버를 따로 띄운 환경(7단계)에서 다시 잰다.
- 메트릭은 서버별로만 모은다. 요청 하나가 게이트웨이 → 주문 → Kafka → 알림을 지나는 경로를 한 줄로 보려면 분산 추적(OpenTelemetry, trace id)이 필요하다.
- 알림(Alert) 규칙은 아직 없다. 운영이라면 p99, 5xx 비율, Outbox 대기 수, DLT 유입에 알림을 건다.
