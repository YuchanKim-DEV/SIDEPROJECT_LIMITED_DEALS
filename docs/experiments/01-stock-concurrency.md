# 실험 01: 재고 동시성

재고 100개 상품에 1,000명이 동시에 1개씩 주문할 때, 재고와 주문 수가 맞는지 본다.

## 환경
| 항목 | 값 |
|---|---|
| 서버 | order-service 1대 (Tomcat 기본 스레드 200, Hikari 커넥션 10) |
| DB | MySQL 8.4.11 (InnoDB, 기본 격리수준 REPEATABLE READ), 로컬 Docker |
| 부하 | `curl` 1,000건, 동시 200건 (`xargs -P 200`) |
| 장비 | MacBook Air M1 (서버, DB, 부하 도구를 한 대에서 실행) |

## 방식 (`POST /api/orders?strategy=...`)
| 방식 | 하는 일 |
|---|---|
| `naive` | 재고를 읽고, 자바에서 빼고, 저장 |
| `atomic` | `UPDATE product SET stock = stock - ? WHERE id = ? AND stock >= ?` 한 문장. 바뀐 줄이 0이면 품절 |
| `pessimistic` | `SELECT ... FOR UPDATE`로 읽는 순간 줄을 잠근다. 다른 주문은 트랜잭션이 끝날 때까지 기다린다(최대 3초) |
| `optimistic` | 잠그지 않고 읽은 뒤 `UPDATE ... WHERE version = 읽은 버전`. 바뀐 줄이 0이면 다른 사람이 먼저 바꾼 것이라 다시 시도한다(최대 50번, 조금씩 다르게 쉬었다가) |

## 다시 돌려보기
```bash
docker compose up -d
set -a; source .env; set +a
./gradlew :order-service:bootRun --args='--spring.jpa.show-sql=false'
scripts/load/oversell.sh http://localhost:8082 100 1000 200 naive    # 또는 atomic
```

## 원인 (대책 없음)
여러 트랜잭션이 같은 재고 값을 동시에 읽고(일반 `SELECT`는 잠그지 않는다), 각자 1을 빼서 덮어썼다. 줄인 기록이 서로 덮여서 사라지는 **갱신 손실(Lost Update)**이다. 트랜잭션은 각자의 작업을 묶어줄 뿐, 동시에 같은 값을 읽는 것은 막지 않는다.

같은 실험인데 초과 판매가 865건, 155건, 654건으로 크게 달랐다. 요청이 겹치는 정도가 매번 달라서다. 처음에는 "서버가 막 켜져서 느렸던 탓"이라고 추측했지만, 서버를 예열한 뒤 돌린 3회차도 654건이라 그 추측은 맞지 않았다. **동시성 버그는 돌릴 때마다 결과가 달라서, 한 번 통과했다고 안전한 게 아니다.** 그래서 해결책은 "가끔 맞는 것"이 아니라 "항상 초과 판매 0"을 기준으로 판단한다.

## 한 줄 UPDATE가 막은 이유
읽기, 빼기, 저장을 DB가 한 문장으로 처리한다. InnoDB는 `UPDATE`하는 줄을 잠그므로, 동시에 온 요청은 앞 요청이 끝날 때까지 기다렸다가 **바뀐 최신 값**으로 `stock >= ?` 조건을 다시 확인한다. 재고가 0이 되면 조건이 거짓이라 바뀐 줄이 0개가 되고, 서버는 이를 품절(409)로 응답한다. 두 번 돌려 두 번 모두 초과 판매 0건이었다.

한계: 재고 차감처럼 **한 문장으로 쓸 수 있는 계산**에만 쓸 수 있다. "회원 등급에 따라 구매 한도가 다르다"처럼 읽은 값으로 복잡한 판단을 해야 하면, 판단 사이에 끼어드는 것을 막을 다른 방법(락)이 필요하다.

## 1-8. 1만 명 비교 (재고 1,000개, 동시 200)
| 방식 | 주문 성공 | 품절 거절 | 기타 | 남은 재고 | 초과 판매 | 걸린 시간 |
|---|---|---|---|---|---|---|
| naive | **9,645** | 355 | 0 | 0 | **8,645** | 49초 |
| atomic | 1,000 | 9,000 | 0 | 0 | **0** | 52초 |
| pessimistic | 1,000 | 9,000 | 0 | 0 | **0** | 38초 |
| optimistic | 1,000 | 8,999 | 1 | 0 | **0** | 39초 |

2026-11-04, 서버를 한 번 예열한 뒤 측정했다.

### 읽는 법
- **정확성**: 막는 세 방식 모두 초과 판매 0건이다. 대책이 없으면 재고 1,000개에 9,645건을 팔았다.
- **걸린 시간은 비교에 쓰지 않는다.** 이 스크립트는 요청마다 `curl` 프로세스를 새로 띄워서, 시간이 서버보다 **부하 도구 자체**에 좌우된다(1만 번 프로세스 생성). 방식별 응답 속도(p95, p99)는 6단계에서 k6로 다시 잰다.
- **optimistic의 기타 1건**: 상태 코드를 기록하지 않아 원인을 확인하지 못했다. 재시도 50번을 모두 실패한 503이었을 가능성이 크다. 이후 스크립트가 기타 응답의 상태 코드를 출력하도록 고쳤다.

### 방식별 장단점
| 방식 | 장점 | 단점 | 어울리는 곳 |
|---|---|---|---|
| atomic | 가장 단순, 잠금 시간이 UPDATE 한 문장뿐 | 한 문장으로 쓸 수 있는 계산만 가능 | 재고 차감처럼 단순한 증감 |
| pessimistic | 읽은 값으로 복잡한 판단을 해도 안전 | 잠근 채로 기다리는 줄이 길어지고, 여러 줄을 잠그면 데드락 위험 | 충돌이 잦고 판단 로직이 복잡할 때 |
| optimistic | 잠그지 않아 충돌이 드물면 빠름 | 충돌이 잦으면 재시도가 폭증(한정판 오픈런처럼 한 상품에 몰리면 불리) | 충돌이 드문 일반 상품, 프로필 수정 |

오픈런은 **한 상품에 요청이 몰리는** 상황이라 낙관적 락은 재시도가 많아지고, 판단 로직이 단순해서 비관적 락까지 필요하지 않다. 그래서 기본 방식은 **atomic**으로 둔다.
