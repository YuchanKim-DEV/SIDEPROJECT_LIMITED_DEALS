# 실험 09: 보안 (JWT, 권한, 입력 검증)과 다시 만난 병목

"남의 주문을 볼 수 있나?" 8단계까지는 **볼 수 있었다.** 게이트웨이와 서버가 손님이 보낸 `X-User-Id` 헤더를 그대로 믿었기 때문이다. 헤더 하나만 바꾸면 누구든 다른 사람이 되어 줄을 서고, 입장권을 쓰고, 주문을 볼 수 있었다.

## 구조
```
손님 ── POST /api/auth/dev-login {userId} ──→ gateway: JWT(HS256, 30분) 발급
손님 ── Authorization: Bearer <JWT> ───────→ gateway AuthFilter (라우팅, Rate Limit보다 먼저)
                                               1. 손님이 보낸 X-User-Id, X-User-Role 무조건 삭제
                                               2. 경로 규칙: 공개 / 로그인 / 관리자 / 서버끼리만
                                               3. 토큰 검증: 알고리즘 HS256 고정, 서명, 발급자, 만료(오차 30초)
                                               4. 통과하면 토큰 주인을 X-User-Id, X-User-Role로 붙여 전달
                                           ──→ 뒤쪽 서버는 이 두 헤더만 믿는다
```

| 경로 | 접근 |
|---|---|
| `/api/auth/**`, `GET /api/products/**`, `GET /api/queue/*/stats` | 공개 |
| `/api/*/admin/**`, `/api/queue/*/simulate`, `POST /api/products`, `/api/notifications/**`, 결제 대사·정산·통계 | 관리자 |
| `/api/queue/*/tokens/validate` | 서버끼리만(밖에서는 404). 열려 있으면 남의 입장권을 맞춰 보는 데 쓸 수 있다 |
| 나머지 `/api/**` | 로그인 (기본은 막는다) |

- 주문 조회 `GET /api/orders/{id}`, 결제 조회 `GET /api/payments/orders/{id}`: **내 것만**. 남의 것이면 403이 아니라 **404**(그 번호가 있다는 사실도 알려 주지 않는다).
- SSE 순번 스트림: 브라우저 EventSource는 헤더를 못 보내서 `?access_token=`으로 받는다. 대기열 서버는 쿼리의 userId보다 게이트웨이가 붙인 헤더를 먼저 쓴다.
- 입력 검증: 로그인 userId는 `[A-Za-z0-9_-]{1,50}`(로그와 Redis 키에 그대로 들어간다), 주문 수량 1~10, Idempotency-Key 1~100자(DB 칸보다 긴 키가 500을 내던 것을 400으로).
- 관리자 로그인: `ADMIN_PASSWORD`를 줬을 때만 열린다. 비교는 `MessageDigest.isEqual`(응답 시간 차이로 한 글자씩 맞히는 공격 방지).
- 키: `JWT_SECRET`(32바이트 이상, 짧으면 시작 실패). 없으면 개발용 키 + 경고 로그. Kubernetes에서는 배포 스크립트가 처음 한 번 무작위로 만든 Secret.

## 다시 만난 병목: 품절 뒤의 줄과 락 안에서 느려진 코드
로그인을 붙이고 1,000명 오픈런을 다시 돌렸더니, 결과(구매 100, 품절 900, 결제 100건 모두 PAID, 대사 불일치 0)는 맞았지만 게이트웨이 3초 시간 초과가 600~750건 나왔다. 실험 06에서는 0건이었다.

**찾은 순서**
1. 게이트웨이 로그: 전부 order-service 호출의 3초 시간 초과.
2. Prometheus: 주문 서버 DB 커넥션 10개 모두 사용, 대기 191개, 요청 스레드 200개 모두 사용. 실험 06의 "한 행 병목"과 같은 모양.
3. 시간 비교: 100건 구매는 3.3초 안에 끝났는데(Outbox 기록 시각), 시간 초과는 **그 뒤 5초 동안** 몰렸다. 품절 이후의 요청이 문제였다.
4. MySQL `information_schema.innodb_trx`를 1초마다 봤다: 재고 UPDATE가 **6~8개씩 락 대기**, 가장 오래된 트랜잭션이 **0.5~1.7초**. 평소에는 몇 밀리초다.

**원인 두 가지**
- **품절된 뒤에도 모두 줄을 섰다.** 재고가 0이어도 주문 요청은 트랜잭션을 열고(멱등 키 저장) 재고 UPDATE를 시도한다. UPDATE는 조건이 맞지 않아도 행을 잠그고 확인하므로, 팔 게 없는 요청 수백 건이 같은 행의 락 앞에 줄을 섰다. 시간 초과 → 클라이언트 재시도 → 같은 줄에 다시 선다.
- **락을 잡은 채로 느린 일을 했다.** 재고 UPDATE(락) 다음에 상품 조회, 주문 저장, Outbox 저장을 했다. 노트북 메모리가 바닥난 상태(남은 메모리 90MB, 압축 3.3GB)에서 JVM이 느려지면, 그 느림이 락을 기다리는 모든 요청에 곱해진다.

**고친 것**
| 변경 | 효과 |
|---|---|
| 품절 빠른 거절: 잠그지 않는 읽기로 재고를 보고 0이면 트랜잭션 없이 409. 단, 멱등 키 기록 확인이 먼저(마지막 재고를 산 사람이 재시도하면 409가 아니라 자기 주문) | 품절 뒤 요청이 락 앞에 서지 않는다. 테스트 추가 |
| 재고 UPDATE를 트랜잭션 **맨 끝**으로(가격 읽기, 주문·Outbox 저장 먼저). 재고가 모자라면 전체가 취소되어 먼저 저장한 것도 남지 않는다 | 락을 잡고 있는 시간이 "UPDATE → 커밋"으로 줄었다 |
| order-service `open-in-view: false` | 요청이 끝날 때까지 커넥션을 붙잡지 않는다(기본은 켜짐) |
| 로컬 실행 힙 상한 `-Xmx384m` | 기본값(메모리의 1/4 = 2GB) × 5개가 8GB 맥에서 스왑을 만들었다 |

**결과 (재시작 직후 첫 1,000명 / 두 번째 1,000명)**
| | 503 | 클라이언트 재시도 | 요청 p99 |
|---|---|---|---|
| 고치기 전 | 616~759 / 0 | 2,290~2,771 | 4.1초 / 1.4~1.9초 |
| 고친 뒤 | 320~387 / 0 | 320~2,141 | 3.2~4.1초 / 2.0초 |

모든 실행에서 데이터는 맞았다(구매 100, 품절 900, 결제 100 PAID, 원장 차변 = 대변). 두 번째 실행은 항상 0건이었고, 재시작 직후 첫 실행만 시간 초과가 남았다. 같은 흐름으로 300명을 먼저 돌려 예열해도 남았다(387건). 메모리가 바닥난 노트북 한 대에서는 JVM 예열, 커넥션·스레드 풀 확장, 메모리 압축 해제가 섞여서 더 나눠 볼 수 없었다. 수치는 그대로 남기고, 서버를 따로 띄운 환경에서 다시 잰다.

## 왜 이렇게 했나
- **왜 게이트웨이에서 검증하나**: 토큰 검사를 서버마다 하면 비밀 키가 모든 서버에 퍼지고, 하나라도 빠뜨리면 구멍이 된다. 입구 한 곳에서 검증하고 뒤쪽은 신뢰하는 헤더만 본다. 대신 뒤쪽 서버에 게이트웨이를 거치지 않고 닿을 수 없어야 한다(Kubernetes에서는 게이트웨이만 밖에 연다. 더 엄격하게는 mTLS나 NetworkPolicy).
- **왜 JWT인가(세션이 아니라)**: 서버가 여러 대여도 공유 저장소 없이 검증할 수 있다. 대신 만료 전에는 취소가 어렵다. 그래서 수명을 30분으로 짧게 두고, 운영이라면 리프레시 토큰과 차단 목록(Redis)을 둔다.
- **왜 HS256인가**: 발급과 검증을 게이트웨이 한 곳에서 하므로 대칭 키로 충분하다. 다른 서버도 검증해야 하면 RS256(공개 키로 검증, 비밀 키는 발급하는 곳만)으로 바꾼다. 어느 쪽이든 헤더의 `alg`를 믿지 않고 기대한 알고리즘으로 고정한다(`alg: none` 공격 테스트).
- **왜 404인가(403이 아니라)**: 남의 주문 번호에 403을 주면 "그 주문은 있다"를 알려 준다. 번호를 1씩 올리며 주문 수를 셀 수 있다(IDOR).

## 한계
- dev-login은 비밀번호 없이 아무 userId로 토큰을 준다. 부하 테스트용이고 운영에서는 끈다(`DEV_LOGIN_ENABLED=false`). 실제로는 회원 서버가 확인한 뒤 발급한다.
- 로그인 경로에는 Rate Limit이 없다(관리자 비밀번호 무차별 대입). 게이트웨이 Rate Limit을 로그인 경로에도 건다.
- 서버끼리의 호출(order → queue 입장권 확인)은 인증하지 않는다. 운영에서는 내부망 분리 또는 서비스 간 토큰을 쓴다.
