# 실험 02: 주문 멱등성

같은 주문 요청이 여러 번 도착할 때(결제 버튼 연타, 응답이 사라져서 클라이언트가 다시 보냄) 주문이 한 번만 생기는지 본다.

## 방식
- 클라이언트가 주문마다 고유한 `Idempotency-Key` 헤더를 붙인다. 같은 주문을 다시 보낼 때는 **같은 키**를 쓴다.
- 서버는 한 트랜잭션 안에서 ① 키를 `idempotency_keys` 테이블에 **먼저** 저장하고(유니크 제약) ② 주문하고 ③ 결과를 키 기록에 적는다.
- 같은 키가 또 오면 ①에서 중복 오류가 난다. 트랜잭션 바깥(`OrderFacade`)에서 이를 잡아 **처음 결과를 200 + `Idempotent-Replayed: true`**로 돌려준다.
- 같은 키가 **동시에** 오면, MySQL(InnoDB)은 두 번째 INSERT를 첫 트랜잭션이 끝날 때까지 기다리게 한다. 첫 요청이 커밋되면 두 번째는 중복 오류를 받고 결과를 다시 받는다.
- 같은 키로 **다른 내용**(상품, 수량)을 보내면 422로 거절한다(요청 지문 SHA-256 비교).
- 주문이 실패하면(품절 등) 키 기록도 함께 취소되어, 같은 키로 다시 시도할 수 있다.

## 다시 돌려보기
```bash
scripts/load/idempotency.sh http://localhost:8082 50 50 with-key   # 같은 키로 50번 동시
scripts/load/idempotency.sh http://localhost:8082 50 50 no-key     # 키 없이 50번 동시
```

## 결과 (2026-11-05, 로컬 MySQL 8.4.11)
| 모드 | 응답 | 실제로 팔린 수 |
|---|---|---|
| 키 없음 | 201 × 50 | **50개** (같은 주문이 50번 생김) |
| 같은 키, 1회차 | 201 × 1, 200(replay) × 49 | **1개** |
| 같은 키, 2회차 | 201 × 1, 200(replay) × 49 | **1개** |
| 같은 키, 다른 수량 | 첫 요청 201, 두 번째 **422** | 1개 |

## 구현 중 겪은 버그
처음에는 같은 키로 두 번째 요청을 보내면 "처리 중(409)"이 나왔다. 원인은 1단계의 한 줄 UPDATE 쿼리에 붙인 `@Modifying(clearAutomatically = true)`였다. 이 옵션이 1차 캐시를 비우면서, 먼저 저장한 키 기록까지 JPA 관리 대상에서 빠졌다(detached). 그래서 결과를 기록에 적어도 변경 감지가 일어나지 않아 DB에 반영되지 않았다. 결과를 적은 뒤 명시적으로 `save`하도록 고쳤다. **변경 감지는 관리 중인 엔티티에만 동작한다**는 것을 테스트가 잡아냈다.

## 한계와 다음 할 일
- 키 기록이 계속 쌓인다. 실제 서비스는 보관 기간(예: 24시간)을 두고 지운다.
- 실패한 요청은 기록하지 않는다. 그래서 같은 키로 다시 보내면 다시 시도된다(품절이 풀렸다면 성공할 수 있다). 실패 결과까지 저장해서 항상 같은 응답을 주는 방식도 있다.
- 지금은 로그인이 없어서 키가 전역으로 유일해야 한다. 사용자 인증이 생기면 (사용자, 키) 쌍으로 묶는다.
