# 실험 04: 이벤트 신뢰성 (Kafka, Outbox, Inbox, DLT)

주문이 확정되면 "주문 확정" 이벤트가 알림 서비스까지 **빠짐없이(유실 0), 한 번씩만(중복 처리 0)** 가는지, 그리고 각 부품이 죽었을 때 어떻게 되는지 본다.

## 구조
```
order-service ── 한 트랜잭션 ──┬─ 재고 차감
                              ├─ 주문 저장
                              └─ outbox_events 저장 (PENDING)
       OutboxRelay(0.3초마다) ─→ Kafka order-events (키 = 상품 id, acks=all, 멱등 프로듀서)
                                       └→ notification-service
                                            한 트랜잭션: notification_inbox(event_id 유니크) 확인·기록 + 알림 저장
                                            실패 → 1초 간격 3번 재시도 → order-events-dlt
```

## 다시 돌려보기
```bash
docker compose up -d           # MySQL, Redis, Kafka
./gradlew bootJar
scripts/run-local.sh start --spring.jpa.show-sql=false
scripts/load/event-delivery.sh # A~E를 순서대로 실행 (Kafka와 알림 서비스를 껐다 켠다)
scripts/run-local.sh stop
```

## 결과 (2026-11-05, 로컬, 2회 실행 모두 같은 결과)
| 실험 | 상황 | 결과 |
|---|---|---|
| A. 정상 | 주문 100건 | 알림 **100건**, 서로 다른 주문 100건. 전달 지연 평균 1.5초, 최대 1.7초 |
| B. Kafka 장애 | Kafka를 끄고 주문 50건 | 주문은 **모두 성공(201)**. 못 보낸 이벤트 50건이 Outbox에 대기. Kafka를 켜자 **5초 만에 50건 모두 전달**, 대기 0 |
| C. 중복 전송 | 보낸 이벤트 30건을 다시 발행(릴레이가 보내고 죽은 상황) | 알림은 **30건 그대로**, 중복 30건을 Inbox가 걸러냄(`notification.duplicates` 30) |
| D. 컨슈머 장애 | 알림 서비스를 끄고 주문 40건 | 다시 켜자 마지막 커밋 위치부터 읽어 **4초 만에 40건 모두 처리** |
| E. 처리 불가 메시지 | 특정 상품 이벤트가 항상 실패하게 설정 | 3번 재시도 후 **DLT로 1건 이동**, 같은 시점의 정상 상품 3건은 **막히지 않고 처리** |

## 구현 중 겪은 문제
- **DLT 이름**: 처음에 DLT 토픽을 `order-events.DLT`로 만들었는데, 메시지가 들어오지 않았다. Spring Kafka 4의 `DeadLetterPublishingRecoverer`는 기본으로 `원래 토픽-dlt`(예: `order-events-dlt`)로 보낸다(예전 버전은 `.DLT`). 실패 메시지는 자동으로 만들어진 `order-events-dlt`에 제대로 들어가 있었다. 이름을 `order-events-dlt`로 통일하고, 옮길 때 ERROR 로그를 남기도록 바꿨다. 확인 도구가 "0건"이라고 할 때 "실제로 안 갔다"고 단정하지 않고 토픽 목록부터 본 덕분에 찾았다.
- **로그 덮어쓰기**: 실험 스크립트가 서버를 다시 띄우면서 로그 파일을 덮어써서, 실패 원인이 사라졌다. 한 번 더 재현해서 확인했다.

## 왜 이렇게 했나
- **왜 Kafka인가**: 주문 확정 이벤트는 알림, 결제, 정산처럼 여러 곳이 받아야 하고 잃으면 안 된다. Kafka는 메시지를 디스크에 저장하고, 받는 쪽이 죽었다 살아나도 어디까지 읽었는지(오프셋)부터 다시 읽는다(실험 D). 같은 키(상품 id)는 같은 파티션으로 가서 순서가 보장된다. Redis Pub/Sub는 저장하지 않아서 받는 쪽이 꺼져 있으면 사라진다.
- **왜 Outbox인가**: 주문 저장(DB)과 Kafka 발행은 한 트랜잭션으로 묶을 수 없다(이중 쓰기 문제). 주문과 이벤트를 같은 DB 트랜잭션에 저장하고 발행은 따로 하면, Kafka가 죽어도 주문은 받고(실험 B) 이벤트는 나중에 반드시 나간다.
- **왜 Inbox인가**: Outbox 릴레이는 "보냄" 표시 전에 죽으면 같은 이벤트를 다시 보낸다(at-least-once). 받는 쪽이 이벤트 id로 한 번만 처리해야 결과가 한 번이 된다(실험 C). 처리 결과와 Inbox 기록을 같은 트랜잭션으로 저장해서, 처리 실패 시 기록도 남지 않게 했다.
- **왜 DLT인가**: 처리할 수 없는 메시지를 계속 재시도하면 같은 파티션의 뒤 메시지가 모두 막힌다. 몇 번 재시도 후 따로 옮겨 두고 넘어간다(실험 E). 원인을 고친 뒤 DLT에서 다시 보내도 Inbox 덕분에 중복 처리되지 않는다.

## 한계
- 전달 지연 1.5초는 릴레이 주기(0.3초) + 컨슈머 폴링 + 로컬 장비 영향이다. 더 줄이려면 Debezium(CDC)으로 binlog를 바로 읽는 방식이 있다.
- 릴레이가 여러 대면 같은 이벤트를 동시에 보낼 수 있다(지금은 Inbox가 막는다). 여러 대로 늘리면 `SELECT ... FOR UPDATE SKIP LOCKED`로 나눠 가지게 한다.
- 로컬에서는 MySQL을 하나 함께 쓰고 테이블만 나눴다(`notification_*`). 운영에서는 서비스마다 DB를 분리한다.
- Outbox와 Inbox 테이블이 계속 커진다. 보낸 지 오래된 행은 주기적으로 지운다.
